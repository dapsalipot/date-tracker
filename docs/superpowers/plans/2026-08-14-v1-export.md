# Receipt Export Implementation Plan (v1, Plan 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn a published date into a stylised receipt image the couple can post — the expense report *is* the keepsake.

**Architecture:** Spec §7.4 splits this into four steps, and only the last two touch the device. `buildReceiptViewModel` is a plain function over the Drizzle client that produces every string and symbol the receipt shows; a template lays that view model out; Skia renders it offscreen at an exact pixel size; the PNG goes to a temp file and out through the share sheet. **The content is asserted in unit tests with no renderer involved** — spec §11 is explicit that we assert the view model, not pixels, because cross-device pixel snapshots are flaky and train developers to ignore failures.

**Tech Stack:** Expo SDK 57 dev build, `@shopify/react-native-skia` (new), `expo-sharing` (new), expo-file-system, drizzle-orm + expo-sqlite (better-sqlite3 in tests), vitest.

## Global Constraints

- `src/domain/**` imports nothing from `react`, `react-native`, or `expo-*`. It runs in plain Node under vitest. This is what makes tier computation and the view model testable in milliseconds with no simulator, and it is the single most important rule in this plan.
- **`src/render/receipt/**` is the only module in the codebase aware that Skia exists** (spec §6, boundary rule 3). Everything else asks for "a shareable image of this date" and receives a file URI.
- Money is always integer minor units. Never floats, never `parseFloat`.
- Deletes are tombstones (`deleted_at`), never `DELETE FROM`. Every read filters them.
- Every write bumps `updated_at` from `deps.clock.nowMs()` — never `Date.now()`.
- Ids come from `deps.newId()` — never generated inside a domain function.
- Aggregations are SQL, never JavaScript `.reduce()`.
- Any query joining a tombstoneable table puts `isNull(x.deletedAt)` in the **ON clause**, not the `WHERE` — in the `WHERE` it silently becomes an inner join and drops parent rows.
- **Tiers are computed at export time and never persisted** (spec §7.5). A shared image is an immutable artifact of that moment; the app makes no promise that a symbol is stable as history grows. No migration in this plan adds a tier column.
- Export sizes are exactly **1080×1350** (post) and **1080×1920** (story).
- Money modes are `exact` | `tier` | `hidden`, defaulting to **`tier`**.
- Colours and spacing come from `src/ui/theme.ts`. Never hardcode a hex value.
- Test runner: `npx vitest run` (**107 passing** at the start of this plan). Type check: `npx tsc --noEmit`.
- **Never run `npm run lint`** — no ESLint config is committed and the command scaffolds one and rewrites `package.json`.
- If vitest fails with `NODE_MODULE_VERSION`, run `npm rebuild better-sqlite3`. That is a known environment issue on this machine (Herd's nvm moves the Node version), not a code problem.

## Two dependencies, and the native rebuild they force

Unlike Plans 1–3, this plan **must** add npm dependencies: `@shopify/react-native-skia` and `expo-sharing`. Both are named in spec §12's v1 stack. Both are native modules, so:

- The app cannot run in Expo Go (already true — `expo-sqlite` settled that).
- An `ios/` directory already exists from an earlier prebuild, which means **adding a native module requires re-running prebuild and reinstalling pods**. The JS will type-check and the unit tests will pass long before the app can actually launch. Task 3 exists to make that gate explicit and to fail loudly rather than at the end.
- Skia was chosen over `react-native-view-shot` deliberately (spec §12): it renders to an offscreen canvas at an exact pixel size regardless of device DPI, so the same date exports identically on a budget Android and an iPhone Pro. Do not substitute a screenshot library.

## Why Tasks 4 and 5 specify behaviour instead of showing code

Every other plan in this project hands the implementer complete code to transcribe. Tasks 4 and 5 do not, and that is deliberate rather than sloppy.

Skia is **not installed yet**, so any component code written here would be invented against an API surface nobody has checked. This project has already been burned once by exactly that: a plan specified `expo-file-system`'s async API, which SDK 57 had removed, and the implementer correctly escalated rather than guessing. Writing plausible-looking Skia JSX now would produce code that must be debugged against reality anyway, while *looking* authoritative enough to discourage checking.

So Task 4 Step 1 makes verifying the installed API an explicit, blocking step with a NEEDS_CONTEXT escape hatch, and Steps 2 onward specify the layout and the invariants precisely — what must be rendered, in what order, from which fields, and what the template is forbidden to compute. Those constraints are the part that matters and the part a reviewer can check. The JSX is transcription either way.

## Deliberately not in this plan

- **Per-person subtotals are structural, not yet meaningful.** v1 has one local user, so every stop has the same `paid_by_user_id` and the subtotal list always has one row. The view model still produces the list, because v2's whole point is that it grows a second row — but no UI work goes into a one-row breakdown.
- **No template picker.** One template ships. Spec §7.4 says "a template selects a layout for that view model"; a chooser with one option is worse than no chooser.
- **No custom fonts in the receipt.** Skia font loading is its own dependency-and-asset problem; the system font renders identically at a fixed pixel size, which is what the export guarantees.
- **No photos in the receipt.** *(Recorded after the fact — this was an undeclared omission the final review caught, not a decision made up front.)* Spec §7.4 calls the export "a stylised **receipt** — the expense report *is* the keepsake", and §2 puts the photo-first treatment on the **feed card**, which is a different render target. A text receipt is therefore defensible on its own terms. But spec §10 says "photos are downscaled **before** compositing", which only makes sense if the export composites photos at all — so the spec does assume imagery here. **This is a real gap, deferred deliberately now that it is visible:** compositing needs image decode, downscale, aspect-fit and a low-memory path, which is its own task rather than a line in the template. Revisit before v1 ships; a receipt with the date's cover photo is a materially better thing to post than one without.

**Why terciles within each kind** (spec §7.5): so ₱₱₱ coffee and ₱₱₱ dinner correctly mean different peso amounts. A single global scale would mark every restaurant meal ₱₱₱ and every jeepney fare ₱, which tells the reader nothing.

**The insufficient-history rule** (spec §7.5): if a kind has fewer than **6** non-deleted stops in the trailing 12 months, that line falls back to `hidden` rather than showing a tier derived from noise. `tierFor` returns `null` for such a kind, and Task 2 renders `null` as no monetary content for that line.

```ts
import { and, asc, eq, gte, isNull } from 'drizzle-orm';
import { dates, stops } from '@/db/schema';
import type { AppDatabase } from '@/db/types';
import type { CoupleScope } from '@/domain/scope';
import { currencySymbol } from '@/domain/money/money';

export type Tier = 1 | 2 | 3;

export interface KindThresholds {
  readonly lower: number;
  readonly upper: number;
}

export type TierTable = ReadonlyMap<string, KindThresholds>;

/**
 * Below this many stops in the window, a kind has no tier at all and its lines
 * render with no monetary content (spec §7.5). Three tiers derived from five
 * points is arithmetic dressed up as insight.
 */
const MIN_SAMPLE = 6;

/** ISO date twelve months before `todayLocal`, computed on the string. */
function twelveMonthsBefore(todayLocal: string): string {
  const [year, month, day] = todayLocal.split('-');
  return `${Number(year) - 1}-${month}-${day}`;
}

/**
 * Thresholds are recomputed on every export and never stored. A shared image is
 * a snapshot of one moment; the app makes no promise that today's ₱₱ is still
 * ₱₱ after another year of dates.
 *
 * The retrieval is SQL. Only the tercile boundary *selection* happens here —
 * that is indexing into a sorted sample, not an aggregation reimplemented in
 * JavaScript.
 */
export function buildTierTable(
  db: AppDatabase,
  scope: CoupleScope,
  todayLocal: string,
): TierTable {
  const rows = db
    .select({ kind: stops.kind, amountMinor: stops.amountMinor })
    .from(stops)
    .innerJoin(dates, and(eq(dates.id, stops.dateId), isNull(dates.deletedAt)))
    .where(
      and(
        eq(dates.coupleId, scope.coupleId),
        gte(dates.occurredOn, twelveMonthsBefore(todayLocal)),
        eq(stops.currencyCode, scope.currencyCode),
        isNull(stops.deletedAt),
      ),
    )
    .orderBy(asc(stops.kind), asc(stops.amountMinor))
    .all();

  const byKind = new Map<string, number[]>();
  for (const row of rows) {
    const bucket = byKind.get(row.kind);
    if (bucket === undefined) byKind.set(row.kind, [row.amountMinor]);
    else bucket.push(row.amountMinor);
  }

  const table = new Map<string, KindThresholds>();
  for (const [kind, amounts] of byKind) {
    if (amounts.length < MIN_SAMPLE) continue;
    // Already ascending: the query orders by kind then amount.
    const lower = amounts[Math.floor(amounts.length / 3)];
    const upper = amounts[Math.floor((amounts.length * 2) / 3)];
    if (lower === undefined || upper === undefined) continue;
    table.set(kind, { lower, upper });
  }

  return table;
}

/** `null` means this kind has too little history to tier — render nothing. */
export function tierFor(table: TierTable, kind: string, amountMinor: number): Tier | null {
  const thresholds = table.get(kind);
  if (thresholds === undefined) return null;
  if (amountMinor <= thresholds.lower) return 1;
  if (amountMinor <= thresholds.upper) return 2;
  return 3;
}

export function tierSymbol(tier: Tier, currencyCode: string): string {
  return currencySymbol(currencyCode).repeat(tier).trim();
}
```

Note `currencySymbol` returns `` `${code} ` `` with a trailing space for unknown currencies. Repeat FIRST and trim after: trimming first collapses tier 3 into `GBPGBPGBP` instead of the legible `GBP GBP GBP`.

```ts
import { and, eq, isNull } from 'drizzle-orm';
import { stops, users } from '@/db/schema';
import type { AppDatabase } from '@/db/types';
import type { CoupleScope } from '@/domain/scope';
import { loadDateDetail } from '@/domain/dates/compose';
import { listStopsForDate } from '@/domain/stops/edit';
import { formatMoney, money } from '@/domain/money/money';
import { buildTierTable, tierFor, tierSymbol } from './tiers';

export type MoneyMode = 'exact' | 'tier' | 'hidden';

export interface ReceiptLine {
  readonly label: string;
  readonly detail: string | null;
  readonly money: string | null;
}

export interface ReceiptPerson {
  readonly name: string;
  readonly money: string | null;
}

export interface ReceiptViewModel {
  readonly title: string;
  readonly occurredOn: string;
  readonly lines: readonly ReceiptLine[];
  readonly people: readonly ReceiptPerson[];
  readonly total: string | null;
  readonly rating: number | null;
  readonly stopCount: number;
  readonly moneyMode: MoneyMode;
}

/**
 * Produces every string the receipt shows, so the export's CONTENT is asserted
 * in plain unit tests with no renderer involved (spec §11). A template must
 * never compute a string this function did not give it — the moment it does,
 * that string is only checkable by looking at pixels.
 *
 * Returns null when the date does not exist or has been tombstoned.
 */
export function buildReceiptViewModel(
  db: AppDatabase,
  scope: CoupleScope,
  dateId: string,
  moneyMode: MoneyMode,
  todayLocal: string,
): ReceiptViewModel | null {
  const detail = loadDateDetail(db, dateId);
  if (detail === null) return null;

  const rows = listStopsForDate(db, dateId).filter(
    (stop) => stop.currencyCode === scope.currencyCode,
  );

  const tiers = moneyMode === 'tier' ? buildTierTable(db, scope, todayLocal) : null;

  const lineMoney = (kind: string, amountMinor: number): string | null => {
    if (moneyMode === 'hidden') return null;
    if (moneyMode === 'exact') return formatMoney(money(amountMinor, scope.currencyCode));
    const tier = tierFor(tiers!, kind, amountMinor);
    // A kind below the sample floor falls back to hidden for that line only.
    return tier === null ? null : tierSymbol(tier, scope.currencyCode);
  };

  const detailOf = (placeName: string | null, subkind: string | null): string | null => {
    const parts = [placeName, subkind].filter((part): part is string => part !== null);
    return parts.length === 0 ? null : parts.join(' · ');
  };

  const lines: ReceiptLine[] = rows.map((stop) => ({
    label: stop.label ?? stop.kind,
    detail: detailOf(stop.placeName, stop.subkind),
    money: lineMoney(stop.kind, stop.amountMinor),
  }));

  // Only `exact` shows any total. In tier mode a grand total would let a reader
  // reconstruct exactly what the tier symbols exist to obscure.
  const showTotals = moneyMode === 'exact';
  const totalMinor = rows.reduce((sum, stop) => sum + stop.amountMinor, 0);

  const paid = db
    .select({ userId: stops.paidByUserId, name: users.displayName, amountMinor: stops.amountMinor })
    .from(stops)
    .leftJoin(users, and(eq(users.id, stops.paidByUserId), isNull(users.deletedAt)))
    .where(
      and(
        eq(stops.dateId, dateId),
        isNull(stops.deletedAt),
        eq(stops.currencyCode, scope.currencyCode),
      ),
    )
    .all();

  const byPerson = new Map<string, number>();
  for (const row of paid) {
    const name = row.name ?? 'Someone';
    byPerson.set(name, (byPerson.get(name) ?? 0) + row.amountMinor);
  }

  const people: ReceiptPerson[] = [...byPerson].map(([name, amountMinor]) => ({
    name,
    money: showTotals ? formatMoney(money(amountMinor, scope.currencyCode)) : null,
  }));

  return {
    title: detail.title ?? 'Untitled date',
    occurredOn: detail.occurredOn,
    lines,
    people,
    total: showTotals ? formatMoney(money(totalMinor, scope.currencyCode)) : null,
    rating: detail.rating,
    stopCount: rows.length,
    moneyMode,
  };
}
```

**On the `reduce`:** the global constraint bans JavaScript aggregation *for analytics queries*, whose SQL must run unchanged against Postgres in v2. This sums an already-fetched array of at most a handful of stops on one date, in the same function that formats them. Re-querying the database to add five integers would be the worse choice. If a reviewer flags this, that is the answer.

export const RECEIPT_SIZES = {
  post: { width: 1080, height: 1350 },

Lay out, in order: the title, the date, a divider, one row per `vm.lines` entry (`label` left, `money` right, `detail` in smaller muted text beneath the label when non-null), a divider, `vm.people` (skipped entirely when every `money` is null and there is only one person — a solo "paid by" line is noise), the total when `vm.total !== null`, and the rating as filled/empty marks when `vm.rating !== null`.

- **Render only strings the view model provides.** Never format a number, never build `'₱' + x`, never compute a total. If you need a string that isn't on the view model, that is a Task 2 gap — report it rather than computing it here.

- Type sizes are absolute pixels for a 1080-wide canvas, not `theme.space` values — the theme's scale is for a ~390pt phone screen and will be invisible here. Roughly: title 72, line label 40, detail 28, total 56.
- Both sizes use the same layout; `story` simply has more vertical room. Do not write two layouts.
